# חיים יחד — הוראות עבודה לבדיקות ושיפור מתמשך

תאריך: 24/09/2026.

## 1. מטרת ההפעלה

פעל כבוחן ומפתח של מערכת חיים יחד. בכל הפעלה מתוזמנת המשך תוכנית בדיקות מתועדת: שלח הודעות WhatsApp אמיתיות מחשבונות הבדיקה, המתן לתגובת הבוט, נתח את איכות השיחה, השווה אותה למידע שנשמר ולפעולות שבוצעו, תקן כשלים מוכחים ובצע בדיקה חוזרת. מרווח ההתעוררות המבוקש הוא עשר דקות; הגדר אותו במנגנון התזמון בלבד.

זהו מסמך הוראות להפעלה עתידית, ולא אישור שבדיקות בוצעו או שתזמון הופעל. מסמך המבנה המשלים הוא `SYSTEM_AND_BOT_BEHAVIOR_HE_2026-09-25_V2.md` באותה תיקייה. הוא מתאר את המימוש שנבדק ואת הפערים הידועים; אין להפוך התנהגות שגויה המתוארת בו לדרישה עסקית.

## 1ב. מקור האמת: השרת החי

כל בדיקת WhatsApp, WAHA, תור, מסד, מדיה וגרסת פרומפט חייבת להתבצע מול שירות חיים יחד שרץ ב־Bluehost. הקוד המקומי משמש לקריאת מימוש, אבחון והכנת תיקון בלבד; תוצאה מקומית אינה הוכחה שהשרת עודכן או שהבוט החי משתמש בה.

בתחילת כל ריצה יש לאמת את כתובת שירות `haim-bot-core`, את נתיב דף הניהול, את `/health` ואת `/ready`, את `WAHA_SESSION=HAIM_YAHAD`, את מצב WAHA ואת schema של המסד הפעיל. יש לתעד את כתובת השירות והגרסה שנמצאו בפועל, בלי לחשוף סודות.

אם כתובת השירות אינה נגישה או אינה מציגה את אפליקציית חיים יחד, התחל אבחון תשתית: אמת את שם המארח מתוך הגדרות השרת בפועל, בדוק DNS, נתיב proxy ו־health/readiness פנימיים. עד לאימות הערוץ החי אין לשלוח הודעות ואין לסמן תרחיש כהצלחה. תעד חסם רק לאחר שמוצו פעולות התאוששות זמינות; המשך עבודה עצמאית שאינה תלויה בערוץ החי.

רק לאחר אימות השרת מותר לבצע את סדר הפעולות: קריאת מצב בשרת → שליחת הודעה דרך WAHA החי → קריאת תשובה → קריאת הרשומה במסד החי → אימות outbox/provider receipt → תיעוד ביומן. בדיקות סימולציה מקומית או בדיקת דף ניהול של שירות אחר אינן מחליפות את הסדר הזה.

מרווח ההתעוררות אינו מגבלת זמן לשיחה ואינו דרישה להשלים את כל שמונת התרחישים בתוך התעוררות אחת. המשך עבודה פעילה ושיחה קיימת לפני פתיחת שיחה חדשה; אל תאתחל את התוכנית בכל התעוררות. מחזור QA יכול להימשך על פני כמה התעוררויות, ובלבד שנשמר checkpoint מדויק ואין ריצות חופפות.

## 1א. לולאת המשך מחייבת

בכל התעוררות, ובכל חזרה לאחר עצירה לא צפויה, בצע את הלולאה הבאה עד שמגיעים לגבול הזמן של אותה ריצה או לחסם אמיתי:

**כלל קדימות:** אם קיימת עבודה פעילה שטרם נסגרה — אבחון, תיקון, build, deploy, retest, regression, reset או תרחיש חי באמצע — התעוררות חדשה היא `RESUME` ולא `RESTART`. אין להתחיל Audit חדש או לנקות ראיות שטרם נשמרו. חסם נקודתי אינו מקפיא עבודה עצמאית; שיחה חיה לא תתקדם כאשר זהות הנמען או מצב שליחה קודמת אינם ודאיים.

1. טען את יומן העבודה, ה־checkpoint ואת מצב WhatsApp/מסד/Outbox בפועל.
2. אם `active_work_state` פתוח, המשך אותו מאותה נקודה. אל תפתח Audit/Reset/תרחיש חדש.
3. אם אין עבודה פעילה אך יש תרחיש פתוח, המשך אותו מהפעולה האחרונה שאומתה. קרא תשובות שכבר הגיעו; אל תשלח שוב הודעה שכבר נשלחה.
4. אם אין תרחיש פתוח, סקור את המחזור האחרון לפי חוזה ה־QA: שיחה Turn-by-Turn, facts, מסד ושליחות.
5. אם נמצא כשל, עבור למצב אבחון/תיקון עד retest ורגרסיה. אם נדרש state נקי לשחזור או ל־retest, שמור קודם ראיות ובצע reset מאומת כחלק מעבודת התיקון. חסם חיצוני יישמר עם `next_action` ו־`retry_at`; המשך משימות שאינן תלויות בו.
6. אם המחזור האחרון נקי וכל העבודה הפעילה נסגרה, בצע QA CLEAN RESET בטוח והתחל/המשך את מחזור שמונת התרחישים הבא בווריאציות חדשות.
7. אם העבודה נעצרה בגלל סיום חלון הריצה, תקלה או ניתוק, שמור checkpoint מדויק. בהתעוררות הבאה ממשיכים מאותה נקודה; אין למחוק את ההתקדמות ואין להתחיל מאפס רק משום שהתרחשה התעוררות חדשה.

### שער אי־חזרת תקלה

- לכל כשל מוכח הוסף לפני התיקון בדיקת רגרסיה קבועה שמייצגת את הקלט/האירוע המדויק שגרם לו, לרבות התוצאה הצפויה בשיחה, במסד ובשליחה הרלוונטית. הבדיקה נשארת ב־suite ואסור למחוק או להחליש אותה כדי לקבל ירוק.
- הוכח RED לפני השינוי ו־GREEN אחריו; אחר כך הרץ את בדיקת הכשל, את כל בדיקות היחידה והאינטגרציה הרלוונטיות, ובכשל הקשור ל־WAHA/DB/Outbox/תמונה/מיקום — גם retest חי שכבות־מלא מול מספרי הבדיקה בלבד.
- בתחילת כל מחזור חדש סקור את מרשם הכשלים ההיסטורי והריץ שוב את בדיקות אי־החזרה המתאימות, גם אם התרחיש הנוכחי הצליח. חזרת סימפטום או פער בין בדיקה מקומית להתנהגות חיה פותחים מחדש את הכשל ומונעים PASS עד תיקון ו־retest.
- תעד מזהה regression קבוע, תוצאות בדיקה, גרסת קוד/שרת וראיית retest. אין לטעון “התקלה לא חזרה” על סמך זיכרון או בדיקה יחידה.

הלולאה נמשכת גם אחרי תרחיש מוצלח; הצלחה אחת אינה תנאי עצירה. אל תשלח את אותו דיווח הצלחה שוב בכל התעוררות. שמור ביומן מתי דווח ולמי. הוראת עצירה חדשה מן המשתמש גוברת על הלולאה.

## 2. תחום הרשאה וגבולות

- חשבונות הבדיקה `0584152101` ו־`0536662043` הם זהויות סימולציה פנימיות שבשליטת המשתמש, ולא אנשים אמיתיים שמחכים לתשובתם. מספר `0543414386` הוא זהות הבוט. מותר וחובה לנהג ה־QA לשלוח דרך הסשנים המורשים את כל תורי הפרסונה הדרושים לתרחיש — לרבות הסכמה, סירוב, תיקון, ביטול, אישור מועד, תמונה ומיקום — כדי להשלים שיחת E2E אמיתית דרך WAHA. אין להמתין לבן אדם שיקליד תשובה בחשבונות אלה, ואין לתאר תשובת פרסונה כתגובה אנושית חיצונית.
- כל שליחה חיה מוגבלת לשלושת המספרים האלה בלבד: חשבונות הבדיקה פונים לבוט, והבוט משיב או פונה רק לשני חשבונות הבדיקה. אין לשלוח לצד אנושי אחר.
- שמות הסשנים הצפויים הם `default` ו־`TAL_ZOLO`; הבוט מופעל דרך `HAIM_YAHAD`. לפני כל אצווה אמת את המספר המחובר לכל סשן ואת מספר הבוט. שם סשן לבדו אינו הוכחה לזהות.
- השאר את סינון הפונים לשני מספרי הבדיקה. אל תפתח מענה לכל הציבור לצורך בדיקה, ואל תשלח לצדדים שלישיים גם אם פרטיהם הופיעו במסד או בשיחה.

- אין להפוך בדיקות להזמנת הובלה אמיתית או להודעה למתנדבים שאינם שני הנבדקים. אם אין הפרדה אמינה ביומן הפעיל, בדוק את השיבוץ בסביבה מבודדת וציין שאין הוכחת שיבוץ חי.
- תיקוני קוד ופרומפט נועדו לממש את הכללים שסוכמו. אין לשנות עצמאית מדיניות עסקית, אזור שירות, שעות, מגבלת קיבולת או הרשאות. סתירה מהותית תירשם כהחלטה נדרשת; המשך בבדיקות שאינן תלויות בה.

## 3. זיכרון העבודה בין הפעלות

נהל יומן מתמשך בתיקיית `docs/qa/` או במיקום מוסכם שאינו נגיש לציבור. היומן חייב להישמר לפני סיום כל הפעלה וגם לאחר כל מעבר משמעותי.

לכל ריצה שמור:

- מזהה ריצה, זמני התחלה ועדכון ואזור זמן.
- גרסת Git מקומית, גרסת שרת מאומתת, מזהה/גרסת פרומפט כשהם נגישים.
- מצב סשנים, מספרים מורשים וגרסת הגדרות משמעותיות, ללא סודות.
- התרחיש הפעיל, שלב השיחה, ההודעה הבאה המתוכננת והסיבה לבחירתה.
- `active_work_state`: אחד מ־`scenario`, `diagnosing`, `fixing`, `testing`, `deploying`, `retesting`, `regression`, `resetting`, `blocked`, או `closed`; תעד גם `next_action`, `last_progress_at`, `retry_at`, בעל הנעילה וסיבת החסם כשישנה.
- מזהי הודעות ספק, פניות, אנשי קשר, מדיה, משימות ושליחות שנוצרו בבדיקה.
- תוצאות, כשלים, תיקונים, בדיקות חוזרות ומשימות שטרם הושלמו.
- רשימת הנתונים שמותר לנקות ורשימת הנתונים שנשמרו לצורך הוכחה.

לכל מקרה בדיקה שמור רשומה עם השדות: מזהה, מסלול, תנאי התחלה, ניסוח שנשלח, תוצאה צפויה, תוצאה בפועל, ראיות שיחה, ראיות מסד, ראיות שליחה, חומרה, גרסת תיקון ומצב.

מצבים מותרים: טרם נבדק, בביצוע, עבר, נכשל, חסום, ממתין לבדיקה חוזרת. אין לסמן ״עבר״ כשאין ראיות.

## 4. מניעת ריצות מתנגשות

הפעל לכל היותר עובד בדיקות אחד על אותם חשבונות ואותו מסד. בפריסת השרת הנוכחית השתמש בנעילת `flock` אטומית על `/run/lock/haim-yahad-qa.lock`; בזמן החזקתה כתוב אטומית ל־`/run/lock/haim-yahad-qa.owner` מזהה בעלים, `acquired_at`, `heartbeat_at` ו־`expires_at` ב־UTC. חדש heartbeat לפחות כל 30 שניות עם תפוגה של 120 שניות. הקובץ לבדו אינו נעילה: רק הצלחת `flock -n` מוכיחה בעלות. כל עובד QA/פריסה חייב להשתמש באותו נתיב. אם הנעילה תפוסה, אל תפרוס או תשלח; קרא את פרטי הבעלים והמתן. אם התהליך הקודם נעלם וה־flock השתחרר, בדוק שאין worker/שליחה פעילים לפני רכישה מחדש. אל תמחק קובץ נעילה כדי לעקוף בעלות.

אם ריצה קודמת פעילה, אל תשלח הודעות ואל תפרוס במקביל. אם הנעילה פגה, בדוק שלא נשאר תהליך פעיל לפני נטילת הבעלות. אל תפרוץ נעילה רק מפני שחלף מרווח ההתעוררות.

אם מופיעה הודעה אנושית חדשה בחשבון הבדיקה, אל תערבב בה הודעות מתרחיש אוטומטי. עצור את השיחה המסוימת, שמור מצב והמשך בבדיקות מבודדות ככל האפשר.

## 5. סדר העבודה בכל התעוררות

1. קרא את היומן, ה־checkpoint ושני מסמכי החובה. רכוש נעילה.
2. אם קיימת עבודה פעילה — המשך אותה בלבד עד נקודת סגירה/אימות סבירה. התעוררות חדשה אינה מאפסת עבודה פעילה.
3. בדוק בריאות שרת, חיבור WAHA, תורים, גישה למסד והגבלת מספרים לפני פעולה חיה רלוונטית.
4. אם אין עבודה פעילה, סקור את כל המחזור האחרון: כל שמונת התרחישים, כולל שיחות שנעצרו באמצע, השיחה Turn-by-Turn, facts, מסד, Outbox ושליחות.
5. חפש במפורש שאלות כפולות, בקשה חוזרת לעיר/כתובת/שם/תמונה שכבר נמסרו, אובדן מידע מהודעה מרובת facts, ערבוב צדדים, פנייה כפולה, עצירה לא טבעית, טענת שליחה ללא ראיה, state ישן או שדה שנשמר בצד הלא נכון.
6. אם נמצא כשל, עבור ל־`diagnosing`/`fixing`; שחזר, תקן שורש, בדוק, פרוס לפי הצורך, בצע retest ורגרסיה. אין לפתוח מחזור חדש עד סגירת העבודה הפעילה. כל retest שמתחיל שיחת WhatsApp חדשה מתחיל לאחר snapshot ראיות ו־QA CLEAN RESET מאומת; אין לנקות באמצע דיאלוג פעיל או כשיש שליחה/עיבוד לא ודאיים.
7. אחרי שיחה מלאה שנסגרה ואומתה, שמור את כל ראיותיה מחוץ למסד ובצע QA CLEAN RESET מאומת לפני פתיחת שיחת E2E חדשה. הדבר חל גם בין תרחישים באותו מחזור: מנקים את נתוני היישום, אך מונה 8/8 והראיות נשמרים ב־checkpoint/יומן החיצוני. אין לבצע reset באמצע שיחה, בזמן עיבוד, כש־Outbox לא הוכרע, או לפני snapshot. רק לאחר שכל 8 השיחות הושלמו ואודיט המחזור נשמר פותחים `cycle_id` חדש ומאפסים את מונה ה־QA ל־0/8.
8. מחזור חדש כולל **שמונה שיחות מלאות — שתי שיחות מכל אחד מארבעת המסלולים**. בכל ריצה יש להמשיך ברצף ולנסות להשלים את כל השמונה; אין לעצור לאחר הודעה אחת, תרחיש אחד או בקשת אישור. אם מגבלת הריצה או תקלה טכנית אמיתית קוטעת את העבודה, המונה וה־checkpoint נשמרים ובהתעוררות הבאה ממשיכים מיד מאותה נקודה עד 8/8; אין לאפס את המחזור ואין להמתין לתגובה אנושית בחשבונות הסימולציה.
9. לכל שיחה בחר וריאציה חדשה לפי המטריצה והיומן. אל תמחזר אוטומטית את אותו ניסוח.
10. בחר כל פעולה לפי התגובה האמיתית; אל תריץ רצף תשובות עיוור.
11. אחרי כל הודעה משמעותית אמת שיחה, facts שנקלטו, מסד ו־side effects.
12. כאשר תרחיש אומת במלואו, דווח `תרחיש [שם] בוצע לגמרי בהצלחה` עם ראיה קצרה והמשך לתרחיש הבא.
13. אם חלון הריצה מסתיים באמצע תרחיש/תיקון/בדיקה, שמור checkpoint והמשך ממנו בהתעוררות הבאה. אין לסמן כשל כמותי רק מפני שה־wake הסתיים.
14. לפני כל אחת משמונה השיחות, לאחר שהקודמת נסגרה ונשמרו ראיותיה, בצע QA CLEAN RESET של כל הנתונים התפעוליים ואמת אפס שיחות/פניות/הודעות/Outbox/מדיה/תורים. הניקוי אינו מוחק את מונה 8/8 החיצוני. לאחר שכל שמונת התרחישים עברו, בצע Audit מלא ושמור ראיות; רק אז פתח מחזור חדש עם מונה QA חדש 0/8. אם נותר קובץ מדיה יתום ב־`haim_core`, ודא שאין לו הפניה ושמור snapshot לפני הסרתו. לעולם אין לנקות בין הודעות של אותה שיחה.

## 6. מטריצת כיסוי וריאציות לארבעת המסלולים

ארבעת המסלולים הם הבסיס לשמונת תרחישי ה־E2E בכל מחזור: שתי וריאציות שונות לכל מסלול. חמש הווריאציות בטבלה הן מאגר כיסוי מחייב לאורך מחזורים, לא דרישה להריץ 20 שיחות בכל התעוררות. יש לסובב ביניהן ולהוסיף וריאציות שנגזרו מכשלים אמיתיים.

מזהי שמונת מקומות המחזור קבועים: `direct-1`, `direct-2`, `open-donate-1`, `open-donate-2`, `self-1`, `self-2`, `request-1`, `request-2`. לכל מקום שמור `cycle_id`, חשבון שולח, וריאציה, תנאי פתיחה, מצב סיום צפוי וראיות. וריאציה אחת בכל מסלול תהיה יחסית מסודרת והשנייה אנושית ומאתגרת. הודעת הכנה או בדיקת health אינה שיחה; שיחה נספרת רק כשהגיעה למצב הסיום העסקי הנכון ונבדקו כל השכבות הרלוונטיות. התאמה משותפת עשויה לשרת שני תרחישים, אבל כל שיחה והאישורים שלה נבחנים ונמנים בנפרד. מחזור עם פחות משתי שיחות שעברו במסלול כלשהו אינו ירוק.

שיחה חיה מתחילה בחשבון בדיקה מחובר, עוברת ב־WAHA אל זהות הבוט המאומתת, נקלטת ב־webhook ועוברת במסלול העיבוד הרגיל עד לתשובת WhatsApp. אחרי כל צעד קרא את התשובה האמיתית ובחר צעד המשך מתאים. בדיקת מנוע מבודדת, seed במסד, בדיקת health או שיגור ידני שעוקף Outbox אינם ראיית E2E. הם רשאים לשמש אבחון ורגרסיה, בתיעוד נפרד.

| מסלול | חמש וריאציות חובה | מצב סיום נכון |
|---|---|---|
| מוסר למישהו מסוים | שם עם שגיאת כתיב וכרטיס קשר; בלי תמונה; תשובות קצרות בצרור; מקבל שמתקן כתובת; ביטול ולאחריו ניסיון חדש | פרטי שני הצדדים ואישוריהם, שיבוץ תקף וסיכום לשניהם; או ביטול עקבי בווריאציית הביטול |
| מוסר בכללי | תמונה לאחר טקסט; תמונה כמסמך; שני רהיטים; היעדר מקבל; התאמה לבקשת בדיקה קיימת | המתנה למקבל כשאין התאמה, או תיאום מלא לאחר התאמה ואישורים |

שיחה תקינה אינה בהכרח תיאום: בקשה ללא רהיט זמין חייבת להישאר בהמתנה. כדי לבדוק תיאום מלא למסלולים הכלליים, צור היצע וביקוש תואמים השייכים לבדיקה בשני החשבונות. אין להכניס אישורים ישירות למסד או לטעון שהבוט אישר דבר שלא עבר בשיחה; כן יש לשלוח דרך WAHA את תשובות פרסונות הטסט, כולל אישורים וסירובים, מפני ששני החשבונות הם חשבונות סימולציה פנימיים.

תרחישי דחייה וביטול נחשבים הצלחת בדיקת מדיניות, אך אינם נספרים כתיאומים מוצלחים. דווח בנפרד על מספר השיחות, בדיקות המדיניות והתיאומים.

## 7. כללי התנהגות שיש לאמת בכל שיחה

- הבוט מבין את הכוונה ומבקש הבהרה קצרה כשיש עמימות; אינו יוצר שתי פניות עבור כוונה אחת.
- קלט כגון ״ישלי מיטה להעביר לט״ יחד עם כרטיס טל מצריך קישור זהיר או שאלה אחת: ״התכוונת למסור לטל, במספר …?״. אסור להחליט על סמך דמיון בשם בלבד כשיש ספק בזהות.
- במסירה ישירה אין לחייב תמונה או לשאול תקינות כתנאי. אל תחיל בטעות את מסלול המסירה הכללית.
- במסירה כללית פעל לפי מדיניות התמונה המאושרת. אין להרחיב או לבטל אותה עצמאית בגלל מבחן שנכשל.
- אין לבקש שוב שם, טלפון, כתובת, תמונה או אישור שכבר נשמרו ונשארו תקפים.
- לאחר קבלת תמונה יש להמשיך לצעד החסר הבא, ולא להמתין ל״נו״ או ״תמשיך״.
- כתובת הכוללת יישוב ורחוב או שכונה מספיקה לפי הכללים; מיקום GPS אינו תנאי נוסף כאשר הכתובת מספקת.
- מספר טלפון מכרטיס קשר נשמר ונשלף גם אחרי הודעות נוספות והפעלת עובד מחדש.
- הצע לפנות לצד השני לאימות, קבל הרשאה ושמור אותה. ״כן״ תקף להקשר הנוכחי בלבד, ואינו אישור כללי לכל פעולה.
- אישור של צד אחד אינו אישור בשם הצד השני.
- נוסח ״נשלחה הודעה״ מחייב ראיית שליחה אמיתית. יצירת משימה או רשומת תור אינה מספיקה; הבחֵן בין בתור, התקבל אצל הספק, נמסר ונקרא.
- אל תשאל פונה למספר פנייה שאין לו כאשר אפשר לזהות אותה מתוך השיחה. אם יש כמה פניות, הצג אפשרויות מובנות.
- שאלות כלליות על השירות אינן צריכות לאפס את תהליך התיאום.
- פתיח הכללים יוצג כשמתאים, בלי לחזור עליו בכל הודעה. נתונים שכבר נמסרו אינם נזרקים בעקבות הפתיח.

## 8. איגוד הודעות, סלנג ותיקונים

בדוק צרור כגון ״שלום״, ״ישלי״, ״מיטה לטל״, כרטיס קשר, ״בלי תמונה היא ראתה״. אמת שהבוט מגיב לכל המידע שהתקבל לפני השליחה ואינו פולט שאלות שכבר נענו.

בדוק גם הודעה שנכנסת בזמן קריאת מודל, תיקון מיד לאחר הודעה, כפל webhook, סדר אירועים שונה ועובד שמופעל מחדש באמצע. הנתונים החדשים צריכים לגבור על הישנים באופן מבוקר, בלי משלוח כפול ובלי אובדן אישורים.

סלנג ושגיאות כתיב חייבים להיבדק בשיחות אמיתיות, לא רק בפנייה מסודרת המכילה את כל שדות המסד. עם זאת, אל תהפוך קלט בלתי ניתן לפענוח לבחינה שמצפה לניחוש; בקשת הבהרה היא התנהגות תקינה.

## 9. כתובות ואזור פעילות

בדוק בית שאן, העלייה, שיכון א׳, רחוב בעל שם לא מוכר, כינוי מקומי, יישובי גבול הפעילות שהוגדרו ומקומות רחוקים כגון עפולה, אילת וירושלים.

אמת מול מאגר ממשלתי מתועד של רחובות/יישובים ככל שקיים, ושמור מקור ותאריך עדכון. מאגר שהועתק מקומית אינו ״בדיקה חיה באתר ממשלתי״. שכונה או כינוי מקומי שאינם במאגר אינם בהכרח כתובת שגויה: יש לשאול פעם אחת לאימות ולאפשר המשך עם סימון שאושר על ידי הפונה.

יש לבדוק איסוף ויעד בנפרד. זיהוי מקום מחוץ לפעילות צריך לקרות גם מתוך תמלול, לפני בקשות מיותרות לתמונה ופרטים נוספים. אין להמציא רדיוס מספרי שלא הוגדר. ״עד כפר רופין, מחולה, ירדנה ובית אלפא״ הוא בסיס מדיניות, לא נוסחת מרחק מאומתת.

## 10. תמונות, מיקומים והקלטות

לכל סוג מדיה בצע מחזור מלא: שליחה, קליטה, שמירה, קריאה חוזרת והחזרה דרך האפשרות הרלוונטית במערכת.

- תמונה רגילה ותמונה שנשלחה כקובץ: אמת סוג תוכן, קישור לפנייה ויכולת הורדה לאחר סיום השיחה. השווה תוכן/מאפיינים; אם הספק דוחס, אין לדרוש hash זהה לקובץ המקורי.
- מיקום: אמת קווי אורך ורוחב, שיוך לאיסוף או ליעד, שמירה ויצירת קישור Waze תקין. בהעברה לעצמו ודא שמיקום היעד לא דרס את האיסוף.
- הקלטה: השתמש בקובץ בדיקה ידוע, בדוק איזה מנוע תמלול עבד בפועל ומה תומלל, ואז בדוק את ההחלטה העסקית. כלול הקלטה עם אילת והקלטה עם כמה רהיטים/תיקון עצמי.
- כישלון הורדה או תמלול צריך להוביל להתאוששות או הבהרה ולא להמצאת תוכן.
- בדוק שליפה דרך `#פניות` ודרך דף הניהול, כולל הרשאה, תצוגה, הורדה והעתקת מיקום; קישור שמחזיר שגיאה אינו הוכחת שמירה תקינה.

## 11. שיבוץ, קיבולת ותיאום

בדוק יום פעילות, חלון שעות, אזור זמן, שבוע הבא מול השבוע הנוכחי, שינוי מועד, עד שני רהיטים לאדם וקיבולת הסבב לפי ההגדרה הפעילה.

המדיניות העסקית שהוגדרה: הובלות בימי שלישי בלבד, בין 16:00 ל־20:00 לפי `Asia/Jerusalem`. ברירת המחדל היא עד 10 הובלות מאושרות בכל יום שלישי. לאחר שהמכסה מלאה, אין להציע שבוע חלופי או לתאם הובלה נוספת אוטומטית: שלח למספר המנהל המורשה בקשת אישור מפורשת להובלה אחת נוספת, והשאר את הפנייה ללא תאריך מתואם עד לתשובת מנהל. תשובת `כן YYYY-MM-DD` מגדילה את המכסה לאותו יום באחת בלבד; `לא YYYY-MM-DD` משאירה את הפניות בהמתנה. כל הובלה נוספת מעבר לכך מחייבת בקשה חדשה ואישור חדש. אמת את המדיניות בפתיח, בהודעות לצדדים, בחישוב התאריך, בהגדרות, בממשק הניהול ובאילוץ המסד. בדוק 19:59 מול 20:00 לפי שעון ירושלים, בקשה 11 ללא אישור, אישור מנהל, דחייה, בקשה 12, כפילויות בקשות, תשובה ממספר שאינו מנהל, ושהודעות לצדדים נשלחות רק בהרשאה.

המנהל שומר על עריכה ידנית בדף הניהול, לרבות `status` ו־`run_date`. עריכה ידנית נרשמת כאירוע מנהל, אינה נחשבת כאישור WhatsApp של המוסר/המקבל ואינה שולחת הודעה לצדדים מעצמה. בעת סימון ידני כמתואמת יש לאמת יום שלישי, תאריך, מצב סבב ומקום פנוי; אין להסיר את יכולת העריכה מה־UI.

לבדיקת קיבולת, בדוק מקום אחרון פנוי, סבב מלא ושתי בקשות מתחרות. אסור שהודעות מקבילות יעקפו את המגבלה. בדוק גם אם מגבלת הפריטים נאכפת לאותו אדם לאורך כמה פניות, ולא רק בכל פנייה בנפרד.

בתיאום מלא אמת: פרטים נשמרו, שתי הסכמות תקפות כשנדרשות, מועד וקיבולת תקפים, סטטוס עקבי, הודעה לשני הצדדים וסיכום מנהל. אישור השתתפות בתפקיד (`approve_self`) ואישור ליצור קשר עם הצד השני אינם אישור למועד. כל צד חייב לאשר במפורש את אותו תאריך מוצע; כל שינוי בתאריך או בפרטים שמשפיעים על ההצעה מבטל את האישורים הרלוונטיים ומחייב אישור מחדש. `run_date` הוא מועד מאושר בלבד; הצעה ממתינה נשמרת ומוצגת בנפרד. אם הסבב מלא, אין להזיז את הפנייה או לתאם אוטומטית: יש להציג הצעה חלופית ולבקש אישורים חדשים. בביטול אמת שחרור קיבולת, עדכון הצד השני והמנהל ומניעת הודעות אישור ישנות מתור שנותר פתוח.

## 12. סיכום למנהל וסדר הובלות

בסיום מחזור מוצלח שמור סיכום בדיקות ביומן. שליחת סיכום WhatsApp למנהל מותרת רק אם מספר המנהל הוא אחד משני מספרי הבדיקה המורשים או אם ה־Runbook עודכן במפורש עם הרשאה נוספת; אחרת אין לבצע שליחה חיה למנהל.

המלצה על סדר נסיעה דורשת בסיס גאוגרפי והסבר על נקודת המוצא והאילוצים. מיון קואורדינטות אינו מסלול מיטבי. אם לא חושבו זמני/מרחקי נסיעה, תאר את התוצאה כהצעת סדר משוערת; אל תטען שהיא הקצרה ביותר. קישורי ניווט יהיו ל־Waze.

אם אין פניות, אין לשלוח סיכום ריק בעקבות איפוס זיכרון. איפוס ניהולי אינו הודעת משתמש ואינו אמור להפעיל שיחה.

## 13. בדיקת שמירה ופעולות — מקור האמת

אחרי כל הודעה שמשנה נתונים בדוק את הרשומה הרלוונטית, לא רק את תגובת הבוט. אמת סוג מסלול, זהות צדדים, פריט וכמות, כתובות נפרדות, מדיה, הסכמות, מצב ותאריך.

אחרי שינוי דרך דף הניהול שאל את הבוט שאלה טבעית על הנתון ושווה למסד. בדוק זאת לכל שדה עסקי ניתן לעריכה באמצעות ערכים חוקיים מסוגו: טקסט בעברית, תאריך אמיתי, מספר תקף או בחירה מותרת. אין להזין עברית לשדה מספרי רק משום שנדרש מבחן בעברית.

בדוק שאנשי קשר משותפים, פניות ותצוגות אינם נשארים עם עותקים סותרים. עריכה לא אמורה ליצור אישור בשם אדם או לשלוח הודעה ללא פעולה מתאימה.

## 14. בדיקות דף הניהול

- כותרות וערכי תצוגה בעברית, בלי לשבור ערכי מערכת פנימיים.
- שדות עסקיים נגישים לעריכה עם ולידציה; שדות טכניים מוגנים עם הסבר.
- לחיצה על טלפון פותחת שרשור מלא רלוונטי, כולל הודעות מערכת שנשלחו מחוץ לתשובה הישירה.
- שליחה מהשרשור מגיעה למספר הנכון בלבד ומתועדת.
- תמונות נראות וניתנות להורדה, מיקומים ניתנים להעתקה ולניווט.
- תאריכים עקביים ולא מחרוזות ISO גולמיות. הכתיב המקובל לשעה הוא HH:mm; בקשת המשתמש המקורית כתבה MM/HH, ולכן יש לתעד את הפרשנות ולא להחליף שעות ודקות בשקט.
- חיפוש בכל העמודות, מיון בכותרות, עימוד של 20 רשומות וכותרת דביקה.
- מחיקה לפי מספר ומחיקה כללית עם אישור ברור בלחיצה, ללא הקלדת מילים; בדוק תחילה את המחיקה הכללית במסד מבודד, ולאחר מכן במסד אפליקציית חיים יחד שאומת כסביבת טסט ורק לאחר שמירת ראיות ובדיקת jobs/Outbox פתוחים.
- בדוק ביטול פעולת מחיקה, קשרי מסד, קבצים, תורים והיעדר שליחות בעקבות איפוס.

## 15. איתור כשל ותיקון

סווג תחילה: קליטת webhook; איגוד הודעות; חילוץ כוונה/פרטים; זיכרון; כללים עסקיים; פרומפט/ניסוח; הרשאת פעולה; מסד/טרנזקציה; תור/שליחה; תצוגת ניהול; תשתית.

אל תנסה לפתור בפרומפט בלבד כשל שבו מספר אינו נשמר, הודעה לא נשלחת או תור נתקע. אל תשנה קוד עסקי כדי להסתיר ניסוח מטעה בלי לתקן גם את הניסוח.

לפני תיקון שמור מקרה משחזר. בצע שינוי קטן, בדיקה ממוקדת ובדיקות רגרסיה. שמור שינויים קיימים של המשתמש. תעד commit וגרסה שנפרסה; אין לטעון שתוקן בשרת משום שקובץ מקומי השתנה.

אתחול שירות הוא פעולת התאוששות, לא הוכחת תיקון. אתחל רק שירות רלוונטי כשיש ראיות לכך שהדבר נחוץ, בדוק תורים ושליחות לא ודאיות לפני ניסיון חוזר ומנע שליחה כפולה. אין לולאת אתחולים בלתי מוגבלת או אתחול של כל השרת כאמצעי ראשון.

## 16. שיפור הפרומפט באופן מבוקר

קרא את הפרומפט הפעיל בפועל אם יש גישה, ואת מזההו וגרסתו בבקשות המערכת. אין להסיק שהוא עודכן רק מפני שבקשת API הצליחה או שהקוד המקומי מכיל הוראות חדשות.

לכל שינוי רשום: הכלל שנכשל, ניסוח קודם, ניסוח מוצע, השפעה צפויה ומקרי בדיקה. שמור גרסה קודמת ואפשרות חזרה. פרסם רק כשקיימת גישת כתיבה מוכחת והרשאה במסגרת המשימה; אם לא, שמור הצעה ואל תטען שפורסמה.

לאחר שינוי בדוק את ארבעת המסלולים, שאלות כלליות, מקרה עמום והודעת מערכת לצד השני. אמת בנפרד שהמערכת משתמשת בגרסה החדשה לניסוח ושהפעולות העסקיות עדיין תקינות. אל תוסיף כללים סותרים כדי לפתור דוגמה אחת.

## 17. הערכת איכות והוכחות

לכל שיחה תן ציון 0–2 בחמישה תחומים: הבנת כוונה, רציפות וללא חזרות, ניסוח והתאמה לכללים, נכונות השמירה, ביצוע פעולות. 0 = נכשל, 1 = חלקי, 2 = תקין עם ראיות.

שיחה נספרת כתקינה לחלוטין רק כאשר כל התחומים הרלוונטיים קיבלו 2, וכל תנאי הסיום של המסלול אומתו. ציון גבוה אינו מפצה על כשל בטיחותי, שליחה לא נכונה, אובדן מידע או אישור שקרי.

לכל הודעה יוצאת רשום בנפרד: `outbox_id`, נמען, מצב התור, ניסיון WAHA, מזהה ספק ורמת ACK שנצפתה. קבלת בקשת השליחה ב־WAHA מוכיחה לכל היותר קבלה אצל הספק; אין לתאר אותה כ־`delivered` או `read` בלי אישור מתאים. אם תוצאת השליחה אינה ודאית, בדוק ספק ושיחה לפני ניסיון חוזר. אין להשלים ראיית צד שני באמצעות שליחה ידנית העוקפת את מסלול הייצור הרגיל.

שמור תמליל מלא עם זמנים וכיוון ההודעות, אך הסר סודות והגבל מידע אישי למינימום הנחוץ. אפשר להציג למשתמש את השיחה עצמה לצד טבלת ״ציפייה/בפועל/ראיה״, לא רק אמירה ש״הכול עובד״.

## 18. המשך לאחר מחזורים מוצלחים

גם לאחר מחזור ירוק אין לסיים את ה־Continuous QA. ההתעוררות הבאה מבצעת Audit מלא למחזור האחרון, QA CLEAN RESET בטוח ומחזור חדש של שמונה תרחישים בווריאציות אחרות.

כאשר הגרסה יציבה לאורך כמה מחזורים, ניתן להעלות את רמת ההקשחה באמצעות וריאציות חדשות, concurrency, recovery, media, timing ו־state transitions — אך אין להחליף את שמונת תרחישי הליבה בבדיקת health בלבד.

אין ליצור עומס מיותר או שליחות מחוץ להרשאה. אם נדרש כיסוי שאינו בטוח לבדיקה חיה, בצע אותו בסביבה מבודדת/קריאה בלבד ותעד זאת במפורש.

## 19. דיווח למשתמש

דווח במפורש על כל תרחיש שהושלם ואומת: ״תרחיש [שם/מזהה] בוצע לגמרי בהצלחה״. אחרי הדיווח המשך לתרגל. עדכן גם על תיקון שנבדק, כשל חדש, השלמת אצווה או חסם שמצריך פעולה. אל תשלח ״עדיין בודק״ בכל התעוררות ואל תחזור על דיווח הצלחה שכבר נמסר.

בכל סיכום הפרד בין: נבדק חי ועבר; נכשל; תוקן מקומית בלבד; נפרס וממתין לבדיקה; חסום. צרף ספירות לפי מסלול ומזהי ראיות. אין להבטיח ריצה ברקע אם מנגנון התזמון לא הופעל ואומת.

## 20. נוסח משימת התזמון

בעת יצירת תזמון בפועל, השתמש בהוראה קצרה שמפנה לשני מסמכי החובה:

> בכל התעוררות פעל לפי `docs/CODEX_HAIM_YAHAD_CONTINUOUS_QA_ORCHESTRATION_HE.md`, ה־Runbook ומסמך ההתנהגות. קרא checkpoint, יומן, שיחה ומצב שרת חי; אמת נעילה וזהויות WAHA. המשך עבודה פתוחה מן הצעד האחרון שאומת בלי לשלוח הודעה שנשלחה כבר. אם אין עבודה פעילה, בצע Audit למחזור הקודם; תקן כשל מוכח, בצע retest ורגרסיה. לאחר שמירת ראיות, בצע QA CLEAN RESET מאומת למסד היישום שהוגדר כסביבת טסט והתחל מחזור חדש של שמונה שיחות WhatsApp חיות, שתיים בכל מסלול; המחזור עשוי להימשך על פני התעוררויות. אחרי כל הודעה בדוק תשובה, facts, מסד ו־Outbox/WAHA. שאלה חוזרת לפרט ברור, איבוד מידע או טענת שליחה ללא ראיה הם כשל. חסם יכיל ראיה, פעולה הבאה ומועד ניסיון חוזר; המשך עבודה עצמאית שאינה תלויה בו. הכרז על הצלחה רק עם ראיות השכבות הרלוונטיות, ושמור מקרה כשל כרגרסיה מחוץ לנתונים המתאפסים. לאחר מחזור ירוק, חזור לביקורת, ניקוי מאומת ומחזור בווריאציות חדשות.

תדירות ההפעלה מוגדרת במנגנון התזמון בנפרד מהמסמך. עצירת המשתמש מבטלת המשך פעולות.

## 21. מחזורי הקשחה מתמשכים

בכל התעוררות יש לאמת מחדש את מצב המערכת ולא להסתמך על דיווח הצלחה קודם. עם זאת, התעוררות חדשה אינה מאפסת מחזור פעיל ואינה מוחקת עבודה פתוחה.

כל מחזור QA כולל שמונה שיחות מלאות: שתי שיחות מכל אחד מארבעת המסלולים. לכל מסלול וריאציה אחת יחסית מסודרת ולפחות וריאציה אחת אנושית ומאתגרת. גוון בשגיאות כתיב, סלנג, קיצורים, facts מרובים באותה הודעה, הודעות מפוצלות, שינוי דעת, תיקון פרט, סדר מידע שונה, הודעה נוספת לפני תשובת הבוט וסתירה שמצריכה הבהרה.

מונה 8 התרחישים נשמר ב־checkpoint/יומן החיצוני בין התעוררויות וגם בין ניקויי מסד של תרחישים. אין “לצבור הצלחות” ממחזורים ישנים, אך מותר וחובה להמשיך את **אותו מחזור פעיל** בהתעוררות הבאה. ניקוי המסד בין תרחישים אינו מאפס מונה QA; רק סגירת 8/8, audit ושמירת ראיות ואז פתיחת `cycle_id` חדש מאפסים אותו.

הצלחה מחייבת שלוש ראיות בכל שלב משמעותי: שיחה נכונה וטבעית; שמירה נכונה במסד; ופעולה חיצונית אמיתית כאשר נדרשת שליחה. אמירת הבוט ששלח אינה ראיה.

כאשר נמצא כשל, המחזור עובר לעבודה פעילה: שחזור → root cause → תיקון → בדיקה → deploy לפי הצורך → retest → וריאציה נוספת → regression. בזמן זה כל wake חדש ממשיך את העבודה הפעילה ואינו מבצע Audit/Reset חדש.

לאחר שכל שמונת התרחישים במחזור עברו, שמור ראיות וסמן את המחזור `completed`. בהתעוררות הבאה סקור אותו מחדש Turn-by-Turn, בצע QA CLEAN RESET בטוח ופתח `cycle_id` חדש עם וריאציות אחרות.

## 22. בדיקת מניעת חזרות ואיגוד כתובת

בכל וריאציה שבה הפונה מסר יישוב, רחוב/שכונה וקומה, בדוק שהבוט אינו מבקש שוב את היישוב או פרט שכבר נשמר. הודעה כגון "בית שאן, רחוב המלך 5, קומה 2" חייבת להישמר כיישוב `בית שאן`, כתובת `רחוב המלך 5` וקומה `2`; "קומה 2" לעולם אינה שם אדם. יש לבדוק זאת גם כשהפרטים מגיעים בשתי הודעות, בסדר הפוך או עם פסיקים וסלנג.

הבדיקה נחשבת ככשל אם היישוב נשאל פעמיים ללא סיבה, שם המקבל מתחלף בטקסט של קומה, הכתובת נשמרת בצד הלא נכון, הקומה נעלמת, או שהבוט אומר שהפרטים נשמרו בלי שהמסד משקף את כל השדות. לאחר תיקון חובה להריץ את המקרה המקורי, וריאציה נוספת עם שם מקבל אמיתי, ורגרסיה למסלולים האחרים.

## 23. שער מעבר בין התעוררויות

כל התעוררות חייבת להסתיים עם checkpoint מפורש באחד המצבים הבאים:

1. **עבודה פעילה נמשכת** — תרחיש/אבחון/תיקון/build/deploy/retest/regression/reset עדיין פתוחים; נשמרה נקודת המשך מדויקת.
2. **תרחיש הושלם** — התרחיש הנוכחי עבר בכל שערי ההצלחה; המחזור ממשיך לתרחיש הבא.
3. **מחזור הושלם** — כל שמונת התרחישים עברו; המחזור מסומן `completed`, וב־wake הבא מתחילים Audit מלא שלו.
4. **Blocked אמיתי** — חסרה גישה/החלטה/תשתית שאינה ניתנת לפתרון במסגרת ההרשאה; נשמרה פעולה מדויקת שנדרשת מהמשתמש.

אסור לסיים התעוררות רק ב“אין שינוי”, “השרת בריא” או “הכול עבר קודם”.

אסור גם לאפס מחזור פעיל רק משום שהסתיים חלון ההתעוררות. מחזור יכול להימשך על פני כמה wakes, כל עוד אותו `cycle_id`, ה־checkpoint והנעילה נשמרים.

לאחר שמחזור הושלם ועבר Audit, בצע QA CLEAN RESET ופתח מחזור חדש עם מונה חדש. לצורך retest של כשל פתוח מותר לבצע reset מוקדם יותר, לאחר שמירת ראיותיו ואימות שאין שליחה קודמת שעדיין עשויה לצאת.
