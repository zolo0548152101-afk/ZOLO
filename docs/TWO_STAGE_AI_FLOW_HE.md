# ניהול שיחת חיים יחד בשתי קריאות AI

## הזרימה הפעילה

לכל הודעת WhatsApp רגילה הזרימה היא:

`WAHA → Action Manager → שמירה ו־commit → Reply Manager → Outbox → WAHA`

1. `prompts/haim-action.he.md` מקבל את ההודעה, ההיסטוריה והמצב ומחזיר רק `commands` ו־`evidence`.
2. הקוד מאמת הרשאות, תקינות, קיבולת ומניעת כפילויות; הוא מבצע ושומר את הפקודות.
3. באותה טרנזקציה נוצר `reply_jobs` עבור מזהה ההודעה. לכן נפילה אחרי השמירה אינה מפעילה שוב פקודות.
4. עובד `reply` קורא מחדש את המצב המאומת ואת תוצאת הפעולות, ואז מפעיל את `prompts/haim-reply.he.md`.
5. ה־Reply Manager מחזיר `messages`: נמען (`sender`, `donor`, `receiver`), מטרה וטקסט מוכן לשליחה.
6. הקוד מאפשר רק את השולח ואת הצדדים של הפנייה, לפי `contact_id` קבוע ולא לפי מזהה WAHA/מספר גולמי. הוא שומר ושולח את הטקסט כפי שהתקבל, עם מפתח מניעת כפילות לפי פנייה, מטרה, נמען וגרסת הפנייה/מועד.

## מה נשאר בקוד

הקוד אינו בוחר מה לשאול או מה לנסח. הוא כן אוכף זהות, הרשאות פנייה לצד שני, תקינות נתונים, קיבולת, ושמירה למסד. הפרומפטים אינם כותבים SQL ואינם יכולים לשלוח לנמען שאינו צד מאומת בפנייה.

הפרומפטים מנוהלים בגיט. מסלולי הפריסה החדשים משתמשים בהם כ־Responses `instructions`; פרומפטים Hosted ישנים אינם משתנים ואינם נבחרים במסלול הזה, כך שניתן לחזור אליהם רק במפורש בעת שחזור.

## תיקון שינוי יעד

כאשר מוסר משנה יעד של מקבל בפנייה ישירה:

- היעד החדש נשמר.
- אישור המועד הקיים נשמר.
- רק אישור הקבלה/הכתובת של המקבל מתאפס.
- ה־Reply Manager מתבקש לייצר בקשת אימות כתובת אחת למקבל. אין לשאול מחדש על יום ההובלה.

בתיאום שהושלם ה־Reply Manager מחזיר סיכום אחד למוסר ואחד למקבל. אם המוסר או המקבל הוא השולח הנוכחי, אותו סיכום הוא גם התשובה לאותו שולח; אין מסלול תבנית נוסף שיוצר הודעה כפולה.

## התאוששות ותפעול

`reply_jobs` הוא תור עמיד. בעבודה מחדש אחרי אתחול, עבודת ניסוח שתקועה ב־`processing` מוחזרת ל־`pending`, ועבודות `pending`/`failed` נכנסות שוב לתור `reply`. לא מבוצעות שוב פעולות השלב הראשון.

הגירה `031_reply_jobs.sql` חייבת לרוץ לפני הפעלה של גרסה זו. אין לשנות פרומפט Hosted, מפתח API או הגדרות WAHA כדי להפעיל את המסלול.
